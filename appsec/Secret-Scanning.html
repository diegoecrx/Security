Secret Scanning

Detection of hardcoded credentials — API keys, tokens, passwords, private keys, connection strings — in source code, configuration and version-control history, with prevention at commit time and a defined response (rotation) for confirmed exposures.

1Definition & scope

Secret scanning detects credentials that have been written in plaintext where they can be read — in source code, configuration, build logs, container images, and version-control history. A valid credential grants access directly, bypassing other controls, so an exposed secret is a high-severity, time-critical finding. The classification is CWE-798 (Use of Hard-coded Credentials).

Two properties distinguish it from other static analysis: it must scan the entire version-control history (a secret removed from the current revision persists in prior commits), and leading tools validate a candidate against the live service to confirm it is active. The definitive remediation is rotation (revoke and reissue), not deletion.

The test is functional, not format-based: if losing it grants access, it is in scope.

3Detection techniques

TechniqueDescriptionTrade-off
Pattern / regex matchingMatch known credential formats (e.g. AWS AKIA…, GitHub ghp_…, Stripe sk_live_…).High precision for known formats; misses custom secrets.
Entropy analysisFlag high-randomness strings lacking a known format.Catches custom secrets; higher false-positive rate.
Validation / verificationTest the candidate against the provider API to confirm it is active.Near-zero false positives on validated secrets; limited to supported providers.

NoteVersion-control history is immutable by default: a secret committed and later deleted remains readable in prior commits to anyone who clones the repository. Removal from the current revision does not neutralize an exposed credential.

5Worked example — exposed cloud access key

# config.py
AWS_ACCESS_KEY_ID     = "AKIAIOSFODNN7EXAMPLE"
AWS_SECRET_ACCESS_KEY = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"   # hardcoded
# Detection
[CRITICAL] AWS Access Key
  file:       config.py (line 2); also present in 3 historical commits
  pattern:    AKIA[0-9A-Z]{16}
  validation: ACTIVE   # confirmed live against the provider API

Correct response, in order: (1) rotate — revoke the key and issue a new one; (2) investigate provider logs for use during exposure; (3) remove from current code and purge from history; (4) move the new credential to a secrets manager. Rotation is step one because it is the only action that neutralizes the exposed key. (The key shown is the vendor's published example, not a live credential.)

6Response & remediation

A confirmed live secret is an incident with a defined lifecycle: detect → rotate → investigate exposure → remove → monitor. Platform-native scanners operate partner programmes with providers (AWS, Stripe, Slack, Google and others) that can automatically revoke a detected token within minutes of exposure. Automated developer notification and a documented runbook ensure every exposure is handled consistently.

7Prevention

  • Push protection / pre-commit hooks — block secrets before they become public; a blocked secret needs no rotation.
  • Secrets manager / vault — the root-cause fix: the code references a secret stored in a vault (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault); nothing sensitive is committed.
  • Allowlisting — durably mark known test/example/placeholder values so they do not re-alert.
  • Short-lived / federated credentials — where available (e.g. OIDC in CI), eliminate long-lived secrets entirely.

8Limitations

  • Custom / low-entropy secrets — a short homemade password with no known format may evade both pattern and entropy detection.
  • Encoded / obfuscated secrets — split or encoded values can evade detection.
  • Non-committed secrets — credentials that live only in runtime memory or a cloud console are out of scope (a secrets-management problem).
  • Detection ≠ remediation — the tool reports; rotation is a separate (sometimes partly automated) action.

10Operational best practices

  • Rotate every confirmed exposure; never treat deletion as remediation.
  • Enable push protection and pre-commit hooks to prevent new exposures.
  • Prioritize validated (active) secrets; use allowlisting to suppress known non-secrets.
  • Run a full-history baseline scan on existing repositories and rotate what it finds.
  • Migrate secrets into a vault; aim for no secrets in source at all.
  • Define an incident runbook; extend monitoring to collaboration tools.

12Terminology & references

Terminology

  • Secret — any credential granting access or proving identity.
  • Secrets sprawl — uncontrolled spread of credentials across repos/tools.
  • Validation — testing a candidate against the live service.
  • Rotation — revoke and reissue a credential.
  • Push protection — blocking a push containing a secret.
  • Allowlisting — suppressing known non-secret matches.
  • Vault — a secrets manager storing credentials outside code.
