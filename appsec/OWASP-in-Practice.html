1What OWASP is & how to use it

OWASP (Open Worldwide Application Security Project) is a nonprofit foundation that publishes free, community-maintained application-security resources: awareness documents, standards, testing guides, maturity models, cheat sheets, and open-source tools. It is the de-facto common vocabulary for application security. Nothing requires payment or membership to use.

The practical skill is matching the right project to the task. The most important distinction:

Resource typeUse it asDo not use it as
Top 10 (web, API)An awareness baseline and risk-prioritization starting point.A complete checklist, a compliance standard, or a test plan.
ASVSVerifiable security requirements and a test basis (what to build/verify).An awareness poster.
WSTGA testing methodology (how to test each requirement).A list of risks.
Proactive Controls / Cheat SheetsDeveloper guidance (how to build it correctly).An audit standard.
SAMMA model to assess and improve the security program.A per-application control list.
NoteThe Top 10 is an awareness document, not a standard. "We cover the OWASP Top 10" is a weak claim on its own; "we verify against ASVS Level 2, test per WSTG, and track maturity with SAMM" is a program. Use the Top 10 to start the conversation, ASVS to make it verifiable.

2OWASP Top 10 (web) applied

The Top 10 is OWASP's flagship awareness document: the ten most critical web application risk categories, revised periodically from industry data. The current released edition is 2021 (editions are updated every few years — verify the latest at owasp.org). Each category below is given with its practical meaning, a concrete example, and the control that prevents it.

OWASP Top 10:2021 — applied
CategoryMeaning & concrete examplePrimary prevention
A01 Broken Access ControlUsers act outside intended permissions: IDOR (read another user's record by changing an id), missing function-level checks, forced browsing to admin routes.Deny by default; enforce object- and function-level authorization server-side on every request.
A02 Cryptographic FailuresSensitive data exposed through weak or absent crypto: plaintext passwords, weak hashing, no TLS, hardcoded keys.Encrypt in transit (TLS) and at rest; hash passwords (argon2/bcrypt); manage keys; classify data.
A03 InjectionUntrusted input interpreted as code/command: SQL, OS command, LDAP; also XSS (untrusted data in output).Parameterized queries; context-aware output encoding; input validation; safe APIs.
A04 Insecure DesignMissing or flawed security design — absent controls, not implementation bugs (e.g. no rate limiting, no authorization model).Threat modeling; security requirements; secure design patterns (see Threat-Modeling reference).
A05 Security MisconfigurationInsecure defaults, verbose errors, open cloud storage, unnecessary features, missing hardening.Hardened, repeatable configuration; minimal surface; config scanning (IaC).
A06 Vulnerable & Outdated ComponentsUsing libraries/frameworks with known vulnerabilities (e.g. Log4Shell via a transitive dependency).Inventory + SCA; patch; SBOM; remove unused dependencies (see SCA reference).
A07 Identification & Authentication FailuresWeak authentication: credential stuffing, weak passwords, broken session handling, missing MFA.Strong auth + MFA; secure session management; rate limiting; vetted identity frameworks.
A08 Software & Data Integrity FailuresTrusting unverified code/data: insecure deserialization, unsigned updates, compromised CI/CD pipeline.Verify integrity (signatures); secure the pipeline; SLSA/provenance (see CI/CD reference).
A09 Security Logging & Monitoring FailuresAttacks undetected: no logging of security events, no alerting, logs that cannot reconstruct an incident.Log security-relevant events; monitor and alert; protect and retain logs.
A10 Server-Side Request Forgery (SSRF)The server is coerced into making requests to unintended destinations (internal services, cloud metadata).Validate/allow-list outbound targets; block internal ranges; segment networks.
In practiceUse the Top 10 three ways: (1) training — a shared baseline for developers; (2) triage — map scanner findings to a category to prioritize; (3) coverage check — confirm each category has a control and a test. For depth, each category links to CWEs and to a Cheat Sheet (Section 7).

3API Security Top 10 (2023)

APIs have a distinct risk profile; the web Top 10 does not cover it fully. Use the API Security Top 10 for any service exposing an API.

IDRiskPractical focus
API1Broken Object Level Authorization (BOLA)The API equivalent of IDOR — verify the caller owns each object.
API2Broken AuthenticationToken/credential handling, weak JWT validation.
API3Broken Object Property Level AuthorizationMass assignment / excessive data exposure at field level.
API4Unrestricted Resource ConsumptionMissing rate limits, pagination, payload limits.

4ASVS — verifiable requirements

The Application Security Verification Standard turns "be secure" into a numbered list of testable requirements. It is how you make security concrete: pick a level, adopt its requirements as acceptance criteria, and verify each. This is the project to standardize on.

LevelForIntent
Level 1All applications; minimumBasic controls, verifiable by black-box testing.
Level 2Most applications (default target)Defense in depth; appropriate for applications handling sensitive data.
Level 3High-value / high-assuranceAdvanced verification for critical systems.

ASVS requirements are grouped by domain — architecture, authentication, session management, access control, validation/encoding, cryptography, error handling & logging, data protection, communications, business logic, files/resources, and API/web services. Each requirement is a single, verifiable statement.

How to use ASVS

  1. Select a level (L2 for most products) and scope it to the application.
  2. Adopt requirements as acceptance criteria — import the relevant requirements into the backlog as security requirements.
  3. Map verification — each requirement is checked by a control + a test (SAST/DAST/manual per WSTG).
  4. Track coverage — report which requirements pass; gaps become work items.
NoteASVS is versioned (4.0.x, with a 5.0 revision released in 2025 that reorganizes the requirements). Pin to a specific version in your program so requirements are stable and auditable, and review on major releases.

5Proactive Controls (build-time)

Where the Top 10 lists risks, the OWASP Top 10 Proactive Controls lists the defensive techniques developers should apply — the "do this" counterpart. Use it as a developer checklist during design and implementation.

IDControlApplies to (Top 10)
C1Define security requirements (use ASVS)A04
C2Leverage security frameworks & librariesA06, all
C3Secure database access (parameterization)A03
C4Encode and escape data (context-aware output)A03 (XSS)
C5Validate all inputsA03
C6Implement digital identity (authn, MFA, sessions)A07
C7Enforce access controls (deny by default)A01
C8Protect data everywhere (crypto, TLS)A02
C9Implement security logging & monitoringA09
C10Handle all errors & exceptionsA05, A09

The Proactive Controls are periodically refreshed; the ten defensive themes above are stable. Pair each with the matching Cheat Sheet for language-specific how-to.

6Testing: WSTG & ZAP

Web Security Testing Guide (WSTG)

The WSTG is OWASP's testing methodology: a structured catalogue of test cases (each with an ID, e.g. WSTG-ATHZ-02) across information gathering, configuration, identity, authentication, authorization, session management, input validation, error handling, cryptography, business logic, client-side, and API testing. Use it to build a repeatable test plan and to ensure each ASVS requirement has a concrete verification procedure.

OWASP ZAP (Zed Attack Proxy)

ZAP is OWASP's flagship DAST tool: an intercepting proxy and automated scanner. In practice:

# Automated baseline scan (passive + safe active) against a running app
docker run -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://localhost:3000 -r zap-report.html

# Full active scan (authorized targets only)
docker run -t ghcr.io/zaproxy/zaproxy:stable \
  zap-full-scan.py -t http://localhost:3000

# API scan from an OpenAPI definition
docker run -t ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py -t https://api.example.com/openapi.json -f openapi

ZAP integrates into CI (see the CI/CD and DAST references). Its findings map to Top 10 categories, giving a direct line from automated testing back to the risk baseline.

9SAMM — program maturity

The Software Assurance Maturity Model assesses and improves the security program (not a single app). It defines five business functions, each with security practices measured at maturity levels 1–3. Use it to baseline where you are and plan where to invest.

Business functionSecurity practices
GovernanceStrategy & Metrics; Policy & Compliance; Education & Guidance
DesignThreat Assessment; Security Requirements; Security Architecture
ImplementationSecure Build; Secure Deployment; Defect Management
VerificationArchitecture Assessment; Requirements-driven Testing; Security Testing
OperationsIncident Management; Environment Management; Operational Management

In practice: run a SAMM self-assessment (the project provides a toolbox/spreadsheet), score each practice, set target levels, and drive a roadmap. It connects the per-app work (Top 10, ASVS) to an organization-level plan.

10Applying OWASP across the SDLC

The projects are complementary; each SDLC phase has a primary OWASP resource. This mapping is the practical heart of "using OWASP".

This maps directly onto the companion references: SAST, DAST, SCA, Secret-Scanning, CI/CD-Security and Threat-Modeling are the techniques; OWASP provides the risk baseline (Top 10), the requirements (ASVS), the test methodology (WSTG), the tooling (ZAP, Dependency-Check), and the program model (SAMM).

11Hands-on walkthrough

A concrete path from zero to a verified finding, using only free OWASP resources.

  1. Stand up a target. docker run -d -p 3000:3000 bkimminich/juice-shop; open http://localhost:3000.
  2. Scan it. Run the ZAP baseline (Section 6) to zap-report.html.
  3. Triage against the Top 10. Map each ZAP alert to a category (e.g. a reflected parameter → A03 Injection/XSS; a missing header → A05).
  4. Pick one finding and confirm it manually using the matching WSTG test case — e.g. test access control (WSTG-ATHZ) by requesting another user's object (A01 / API1 BOLA).
  5. Write the requirement. State the fix as an ASVS requirement (e.g. "verify object-level authorization on every data access") and add it as acceptance criteria.
  6. Find the control. Open the relevant Cheat Sheet (e.g. Authorization, SQL Injection Prevention, XSS Prevention) for the implementation pattern.
  7. Remediate & retest. Apply the fix in your own code; re-run ZAP and the WSTG test; confirm the finding is gone.
  8. Record maturity. Note the activity against SAMM Verification — Security Testing.

Repeat on the SecureBank project (appsec/project/) to practice the same loop on an application whose vulnerabilities you introduced deliberately and can fix cleanly.

12Best-practice checklist

Adopt

  • Use the Top 10 for awareness and triage, not as the whole program.
  • Standardize on ASVS (Level 2 default) for verifiable requirements.
  • Add the API Security Top 10 for any API.
  • Use Proactive Controls + Cheat Sheets as the build-time how-to.

Test

  • Build a test plan from WSTG; automate with ZAP in CI.
  • Map every finding to a Top 10 category and an ASVS requirement.

Operate & improve

  • Scan dependencies (Dependency-Check); monitor via Dependency-Track + CycloneDX SBOM.
  • Threat-model with Threat Dragon.
  • Consider CRS as runtime defense-in-depth (not a code-fix substitute).
  • Assess and plan the program with SAMM.
  • Practice continuously on Juice Shop / WebGoat.
