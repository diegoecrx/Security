Threat Modeling

1Definition & scope

Threat modeling is the structured identification of how a system could be attacked, performed at design time, so that mitigations are designed in rather than retrofitted. It is the earliest security activity in the SDLC — it operates on architecture and data flow before code exists — and finds a class of defect the scanners cannot: design flaws and missing controls (e.g. an unauthenticated interface, absent authorization, unencrypted sensitive data). It produces security requirements that SAST/DAST later verify were implemented correctly.

2Process

The widely used framing is four questions; the artifacts and methods below answer them.

QuestionActivity / artifact
1. What are we building?Model the system with a Data Flow Diagram (DFD): external entities, processes, data stores, data flows, and trust boundaries (where control changes hands). Identify assets and entry points.
2. What can go wrong?Elicit threats per element using a methodology (STRIDE) and/or abuse/misuse cases.
3. What are we going to do about it?Rank by risk; decide per threat: mitigate, accept, transfer, or eliminate. Mitigations become security requirements.
4. Did we do a good job?Review coverage and mitigations; maintain the model as the design changes.

Threats concentrate at trust boundaries, where data crosses from a less-trusted to a more-trusted context.

5Worked example — login + user database

DFD: External entity User → process Web application → data store User database. Trust boundaries: internet→server, and application→database. STRIDE applied per element yields threats and required controls:

STRIDEThreat on this systemRequired control
SpoofingAuthentication with stolen/guessed credentialsMFA; credential-stuffing/brute-force protection
TamperingMalicious input alters a DB query (SQL injection)Parameterized queries; input validation
RepudiationUser denies an action; no recordAudit logging of security events
Information disclosureCredentials intercepted; database exfiltrated in plaintextTLS; password hashing; encryption at rest
Denial of serviceLogin endpoint floodedRate limiting; scaling
Elevation of privilegeNormal user reaches admin functionEnforced authorization; least privilege

Each control becomes a security requirement defined before implementation.

7Risk analysis & prioritization

Threats are prioritized by likelihood × impact, optionally scored with a scheme such as DREAD or a CVSS-style rubric. Each threat receives a risk response (mitigate / accept / transfer / eliminate). Mitigations are tracked to completion; the risk remaining after mitigation — residual risk — is formally recorded and accepted by an owner. Security decisions are captured in Architecture Decision Records (ADRs).

8SDLC integration & limitations

When: at design of a new system/feature, and on significant change (new trust boundary, new data type, new integration, architecture shift). Who: developers, architects, security and product together — the breadth of perspective drives coverage. Integration: a review gate in the design process; findings become backlog items; models are revalidated as living artifacts. Threat-model-as-code (pytm, Threagile) keeps models in version control.

Limitations: the output quality is subjective and bounded by participants' knowledge; threats outside the team's awareness are missed; it requires skilled facilitation and ongoing maintenance; and its value depends entirely on the identified mitigations being implemented and tracked.

10Operational best practices

  • Keep sessions lightweight and timeboxed; model the risky parts, not everything.
  • Use STRIDE plus a simple risk ranking as the default; add PASTA/LINDDUN/attack trees where warranted.
  • Include developers, architects, security and product in the session.
  • Convert every mitigation into a tracked backlog item; record residual risk and ADRs.
  • Make threat modeling a gate in design review; revalidate on significant change.
  • Maintain models as living artifacts, ideally as code in version control.

12Terminology & references

Terminology

  • DFD — data flow diagram of components and flows.
  • Trust boundary — where trust level changes.
  • Asset — something worth protecting.
  • Attack surface — all points an attacker can reach.
  • Abuse/misuse case — adversarial inverse of a use case.
  • Residual risk — risk remaining after mitigation.
  • ADR — architecture decision record.
