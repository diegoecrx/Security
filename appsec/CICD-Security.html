CI/CD Security (DevSecOps)

Securing the software delivery pipeline along two dimensions: integrating security testing into the pipeline (automated gates), and hardening the pipeline itself against compromise (a privileged, high-value supply-chain target). Covers architecture, threats, hardening, provenance, tooling and practice.

1Definition & the two dimensions

CI/CD security addresses the automated pipeline that builds, tests and deploys software. It has two distinct objectives, each with its own threat model:

DimensionObjectiveFailure mode
Security in the pipelineRun automated security checks so defective code cannot progress ("shift left").Vulnerable software ships.
Security of the pipelineHarden the build system, its credentials and components against compromise.A single compromise poisons every artifact produced (one-to-many breach).

The pipeline holds source code, signing keys and production credentials — more privilege than most individual accounts — and its output is automatically trusted downstream. This makes it a primary target (SolarWinds, Codecov, tj-actions).

2Security in the pipeline (gates)

A security control is attached at each stage. Each gate is a technique from the reference set, run automatically:

StageGateChecks
CommitSecret scanning (pre-commit / push protection)No credentials enter history
BuildSCA + SASTVulnerable dependencies; code-level defects
TestDAST / IASTRuntime-exploitable defects on a deployed build
ReleaseContainer image scan + artifact signing + SBOMImage vulnerabilities; integrity; inventory
DeployIaC scan + admission policyInfrastructure misconfiguration; signed-only deploys

A gate that detects a critical issue stops progression (the quality gate). Findings feed back to developers; continuous monitoring re-opens the loop when a new advisory affects a shipped artifact.

Most of these concern access, trust and configuration — not application code — which is the common blind spot.

4Supply-chain attack example — tj-actions/changed-files (CVE-2025-30066)

In March 2025 a widely used GitHub Action (present in 20,000+ repositories) was compromised. Sequence:

  1. A leaked token for the action's repository was obtained.
  2. A malicious commit was added, and existing version tags were re-pointed to it.
  3. Consuming pipelines pulled the "updated" action and executed it.
  4. The injected script extracted CI/CD secrets from the runner into build logs (public logs exposed them).

Root cause: trusting a mutable version tag of a third-party action rather than pinning an immutable commit hash. No first-party application code was defective; the pipeline's trust in an external component was the vulnerability. Pinning to a full commit SHA would have blunted it.

5Pipeline hardening

ControlFunction
Pin dependencies & actionsReference third-party components by immutable commit hash, not a movable tag (mitigates SEC-3, the tj-actions class).
Least privilege (PBAC/IAM)Grant each job the minimum scope; restrict secret access so one step cannot reach everything.
Short-lived credentials (OIDC)Mint per-run identity tokens that expire in minutes; eliminate long-lived stored keys.
Service accounts & token managementGive the pipeline a dedicated scoped identity; inventory, rotate and revoke tokens.
Ephemeral, hardened runnersFresh, disposable build hosts with egress controls; malware cannot persist.
Environment separationIsolated dev / staging / production with distinct controls and credentials.
Flow control & reviewRequired review and status checks before merge; deployment approvals before production.
Audit logging & monitoringTamper-evident record of who ran what, when; alert on anomalous runs.

6Provenance & integrity (SLSA)

Integrity controls prove that a deployed artifact is the unmodified output of a known build from known sources. Artifact signing (e.g. Sigstore/cosign) and provenance attestations bind an artifact to its build. SLSA (Supply-chain Levels for Software Artifacts) grades build integrity in levels, from no guarantees to non-falsifiable provenance from a hardened build. Admission policy at deploy time accepts only signed artifacts with valid provenance. SBOMs are generated and distributed alongside releases. These controls align with NIST SSDF and are increasingly required contractually.

7Gates, policy & governance

  • Security quality gates — fail the build or block the merge above a defined severity/confidence threshold.
  • Vulnerability thresholds — explicit criteria for what blocks vs. warns.
  • Risk acceptance / exceptions — documented, time-boxed, approved deviations.
  • Deployment approvals — a named human gate before production promotion.
  • Audit logging — evidence for compliance and incident reconstruction.
CautionGating on fast, high-confidence signals is effective; gating on slow or noisy checks trains teams to bypass the pipeline. Deep or noisy analysis belongs off the blocking path (asynchronous/scheduled), not in every build.

8Constraints

  • Speed vs. assurance — the pipeline exists to deliver quickly; gates add latency. Placement (block vs. warn vs. async) must respect this or controls get disabled.
  • Dependence on the gates — pipeline security is only as good as the scanners and rules it runs.
  • Complexity & third-party trust — many components and plugins to vet; each is attacker-reachable code with access.
  • Blast radius — a compromised pipeline is a one-to-many event and can operate undetected without logging.

10Operational best practices

  • Run security gates in warn mode first; enforce on criticals once tuned.
  • Pin all third-party actions/components to immutable hashes.
  • Replace long-lived CI secrets with OIDC short-lived credentials.
  • Apply least privilege to jobs and secrets; separate environments.
  • Sign artifacts, generate provenance and SBOMs; enforce signed-only deployment.
  • Require review and production deployment approvals; enable audit logging and anomaly alerting.
  • Provide golden/hardened pipeline templates so the secure path is the default.

12Terminology & references

Terminology

  • Runner / agent — host that executes pipeline jobs.
  • PPE — poisoned pipeline execution.
  • Dependency confusion — public package shadows an internal one.
  • Pinning — referencing an immutable version (commit hash).
  • OIDC federation — short-lived per-run identity tokens.
  • Provenance — verifiable record of how an artifact was built.
  • SLSA — Supply-chain Levels for Software Artifacts.
