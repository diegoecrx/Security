1Definition & scope

DAST tests a running application from the outside, without access to source code. It sends HTTP requests — including crafted attack payloads — and analyses the responses for evidence of a vulnerability. Because it has no internal visibility and interacts only through exposed interfaces, it is a black-box technique that approximates an external attacker's perspective.

DAST requires a deployed target (test, staging, or a controlled production scope), typically valid credentials for authenticated areas, and explicit authorization to test. It operates at the Test / pre-production stage and confirms real, reproducible exploitability on the running system. It is complementary to SAST (source analysis), SCA (components) and secret scanning.

2Testing mechanism

  1. Discovery / crawling — spider the application (follow links, submit forms, parse API definitions) to enumerate the reachable attack surface: endpoints, parameters, headers. Authenticated crawling requires session handling.
  2. Input identification — catalogue every injectable point (query/body parameters, headers, cookies, path segments).
  3. Passive scanning — inspect normal traffic for defects without attacking: missing security headers, insecure cookie flags, information disclosure, weak TLS.
  4. Active scanning — inject attack payloads (fuzzing) into each input to provoke a detectable condition.
  5. Response analysis (oracle) — determine success from the response: reflected payload, error signature, time delay (time-based), status change, or an out-of-band callback.
  6. Confirmation — replay to verify reproducibility (proof-based scanning), reducing false positives.
NoteActive scanning is an attack. It must be run only against authorized targets, and its side effects (form submissions, state changes, emails, rate-limit consumption) make test environments with disposable data the default target rather than production.

5Worked example — reflected XSS (CWE-79)

The scanner identifies a search parameter, submits a script payload, and inspects the response for unencoded reflection.

# Attack request
GET /search?q=<script>alert(1)</script> HTTP/1.1
Host: shop.example.com

# Response (excerpt)
HTTP/1.1 200 OK
Content-Type: text/html
...
<h2>Results for: <script>alert(1)</script></h2>   # reflected unencoded → executes in-browser
WeaknessCWE-79 — Reflected Cross-Site Scripting High
LocationGET /search, parameter q
EvidencePayload reflected into HTML response body without output encoding
RemediationContext-aware output encoding; Content-Security-Policy as defence in depth

DAST reports the reproducing request. It identifies the vulnerable endpoint and parameter but not the responsible source line — root-cause localization is a SAST/code-review task.

6Scan configuration & coverage

  • Authenticated vs. unauthenticated — most of an application's surface and risk is behind authentication. The scanner must log in, maintain a session, and detect/avoid logout; a scan that cannot authenticate tests only public endpoints.
  • Crawl completeness — undiscovered endpoints are untested (the primary false-negative source). Seed the crawler with URLs, an OpenAPI/GraphQL schema, or a recorded session; use a JS-capable crawler for SPAs.
  • Scope & safety — constrain target hosts/paths; set rate limits; exclude destructive operations.
  • Policy — select active vs. passive rules per environment.

8Limitations

  • Coverage-bound false negatives — only tested what it reached and crawled; undiscovered endpoints are silently untested.
  • No source localization — reports URL/parameter, not the responsible code.
  • Late stage — requires a deployed, working environment; fixes are more expensive than at code stage.
  • Operational risk — active scanning can disrupt the target and generate junk data; requires authorization and scoping.
  • Weak on business logic — cannot reason about intended behaviour; complemented by manual testing.

10Operational best practices

  • Obtain written authorization and define scope before any active scan.
  • Configure authenticated scanning; verify the session holds throughout.
  • Seed the crawler with API/GraphQL schemas and recorded sessions for coverage.
  • Prefer tools that validate/reproduce findings; gate only on confirmed high/critical.
  • Scan against test/staging with disposable data; rate-limit and exclude destructive paths.
  • Assign severity-based remediation SLAs; correlate findings with SAST for root cause.
  • Supplement automated DAST with periodic manual penetration testing for logic flaws.

12Terminology & references

Terminology

  • Black-box — testing with no internal visibility.
  • Attack surface — the set of reachable, interactable inputs.
  • Crawling / spidering — automated discovery of endpoints.
  • Passive vs. active scan — observe traffic vs. inject payloads.
  • Fuzzing — sending many payload variations to an input.
  • Oracle — the response signal confirming a payload worked.
  • Proof-based scanning — reproducing a finding before reporting.
  • Authenticated scan — scanning with a valid session.
