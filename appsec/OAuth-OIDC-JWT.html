OAuth 2.0, OpenID Connect & JWT

Three distinct specifications: OAuth 2.0 (delegated authorization), OpenID Connect (authentication on top of OAuth), and JSON Web Token (a token format). Covers roles, the Authorization Code + PKCE flow, token types, JWT structure and validation, security pitfalls, standards and tooling.

1The three specifications

These are frequently conflated but address different concerns. Two are purposes; one is a format.

SpecificationConcernFunction
OAuth 2.0 (RFC 6749)Authorization (AuthZ)Delegated, scoped access to a resource on a user's behalf without sharing credentials. Produces an access token.
OpenID ConnectAuthentication (AuthN)Identity layer on top of OAuth 2.0; establishes who the user is. Produces an ID token.
JWT (RFC 7519)Token formatA signed, compact container for claims. The format OIDC ID tokens use and OAuth access tokens may use; also used independently.

OIDC reuses OAuth's flows and adds the ID token and a userinfo endpoint. A common error is using an OAuth access token for authentication (determining identity); that is OIDC's purpose, not OAuth's.

3Authorization Code flow with PKCE

OAuth 2.1 consolidates current best practice on a single flow for user-facing clients (web, SPA, mobile): the Authorization Code flow with PKCE (Proof Key for Code Exchange, RFC 7636).

  1. Client generates a code_verifier and its hash, code_challenge.
  2. Client redirects the user to the authorization server's /authorize endpoint with client_id, redirect_uri, scope, state, and code_challenge.
  3. User authenticates at the authorization server and consents.
  4. Authorization server redirects back to redirect_uri with a short-lived authorization code and the state.
  5. Client verifies state, then POSTs to /token with the code and code_verifier.
  6. Authorization server validates the verifier against the challenge and returns an access token, a refresh token, and (for OIDC) an ID token.
  7. Client validates the ID token; calls the resource server with the access token.
NotePKCE binds the authorization code to the client that initiated the flow. An intercepted code cannot be exchanged without the matching code_verifier. OAuth 2.1 makes PKCE mandatory for all clients. The user's credentials are entered only at the authorization server; the client never receives them.

Crossing token purposes — sending an ID token to an API, or using an access token to identify the user — is a common defect.

6JWT structure

A JWT is three Base64URL-encoded segments separated by dots: header.payload.signature. The header and payload are encoded, not encrypted — readable by any holder.

// header
{ "alg": "RS256", "kid": "abc123" }
// payload (claims)
{
  "iss": "https://issuer.example.com",   // issuer
  "aud": "client-id",                    // audience (intended recipient)
  "sub": "1076915003",                   // subject (user id)
  "exp": 1733600000,                      // expiry
  "nonce": "a7f3..."                     // binds token to a login request (OIDC)
}
// signature: over header + payload, verified with the issuer's public key
CautionA JWT is signed, not encrypted, by default. Do not place secrets in the payload; transmit only over TLS.

7JWT validation

Accepting a JWT without full validation is the root cause of most token-based account-takeover defects. A compliant validator must:

  1. Verify the signature using the issuer's current public key, obtained from its JWKS endpoint (cache keys; handle kid rotation).
  2. Reject alg: none and pin the expected algorithm.
  3. Validate iss (expected issuer), aud (this client/API), and exp (not expired).
  4. Validate nonce for OIDC authentication flows.

9Operational constraints

JWT revocation: a self-contained signed token is verifiable offline without contacting the issuer — which also means it cannot be easily revoked before expiry. Mitigations: keep access tokens short-lived (minutes) and revoke via refresh-token invalidation; or use token introspection / a denylist where immediate revocation is required. This trade-off (offline verification vs. revocation) is inherent to stateless tokens.

11Best practices

  • Use a vetted authorization server and client library; do not implement the protocol from scratch.
  • Use Authorization Code + PKCE for user-facing clients; Client Credentials for machine-to-machine; avoid removed grants.
  • Validate every token fully (signature via JWKS, iss, aud, exp, nonce); reject alg: none.
  • Exact-match redirect_uri; use and verify state; request least-privilege scopes.
  • Keep access tokens short-lived; store tokens in secure, HttpOnly cookies; never in URLs.
  • Transport exclusively over TLS; do not place sensitive data in JWT payloads.

12Terminology & references

Terminology

  • AuthN / AuthZ — authentication / authorization.
  • Scope — a named permission requested by a client.
  • Claim — a field within a token.
  • PKCE — proof key for code exchange.
  • JWKS — issuer's published public-key set.
  • Nonce — single-use value binding a token to a login.
  • FAPI — financial-grade API security profile.
