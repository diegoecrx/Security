2Concepts & terminology

TermDefinition
Repository (repo)A project's version-controlled file tree and history.
CommitAn immutable snapshot of changes with a message.
BranchA movable pointer to a line of commits; isolates work in progress.
RemoteA hosted copy of the repository (e.g. on GitHub); origin by convention.
Pull request (PR)A proposal to merge one branch into another; the unit of review and the trigger for CI checks.
CI / CDContinuous Integration (merge + automatically build/test often) / Continuous Delivery or Deployment (automatically release).
Pipeline / workflowThe automated sequence run on events; in GitHub Actions a workflow is a YAML file of jobs and steps.
RunnerThe machine that executes a job (GitHub-hosted or self-hosted).
Image / containerA packaged, immutable filesystem + metadata (image) and a running instance of it (container).
RegistryA store for images (e.g. GHCR, Docker Hub); images are pushed to and pulled from it.
ArtifactA build output passed between jobs or retained after a run.
ComposeA tool that defines and runs a multi-container application from one file.
EnvironmentA named deployment target (dev/staging/prod) with its own secrets and protection rules.
SecretA credential supplied at runtime, never committed to the repository.

3Repository setup from zero

# Initialize locally
git init
git branch -M main
git add -A
git commit -m "Initial commit"

# Create the GitHub repo and push (GitHub CLI)
gh repo create my-app --private --source=. --remote=origin --push

# Or add an existing remote manually
git remote add origin git@github.com:<user>/my-app.git
git push -u origin main

Branch strategy

For most projects use trunk-based development: a protected main, short-lived feature branches, merged via PR. Reserve long-lived release branches (Git Flow) for products with parallel supported versions.

# Feature branch workflow
git switch -c feat/login
# ... commit work ...
git push -u origin feat/login
gh pr create --fill          # open a PR; CI runs on it

Branch protection

On main, require: a PR before merge, passing status checks (the CI pipeline), at least one review, and a linear/up-to-date history. This makes the pipeline the enforced quality gate.

NoteAdd a .gitignore before the first commit to avoid committing build output, dependencies and local config. Add a LICENSE and README.md at creation; they are expected of any public project.

5Containerization (Docker)

A container packages the application and its runtime so it runs identically on any machine and in CI. Define the build in a Dockerfile; exclude noise with .dockerignore.

# Multi-stage build: smaller, no build tools in the final image
FROM python:3.12-slim AS base
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1

FROM base AS deps
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM base AS runtime
WORKDIR /app
# copy installed packages from the deps stage
COPY --from=deps /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY src/ ./src
# run as a non-root user
RUN useradd -m appuser
USER appuser
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s CMD curl -f http://localhost:8000/health || exit 1
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
Dockerfile best practices
PracticeReason
Pin a specific base image tag (or digest)Reproducible builds; avoid silent upstream changes.
Multi-stage buildsKeep build tools out of the final image; smaller, smaller attack surface.
Run as a non-root userLeast privilege inside the container.
Copy dependency manifests before sourceLayer caching: dependency layer is reused when only code changes.
Use .dockerignoreExclude .git, .env, node_modules, tests from the build context.
Add a HEALTHCHECKLets the orchestrator know when the container is ready/healthy.
No secrets in the imageImages are distributable; inject secrets at runtime (Section 7).

6Compose & environment segregation

Docker Compose defines a multi-service application (app, database, cache) in one file and wires their networks and volumes. Segregation applies at three levels: service networks, per-environment configuration, and per-environment secrets.

# docker-compose.yml  (base definition)
services:
  api:
    build: .
    env_file: .env
    depends_on: [db, redis]
    networks: [frontend, backend]
    ports: ["8000:8000"]
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    networks: [backend]            # NOT on frontend: not reachable from the edge
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7
    networks: [backend]

networks:
  frontend:
  backend:
    internal: true                 # backend network has no external egress
volumes:
  pgdata:

Segregation techniques

TechniqueEffect
Separate networksThe database/cache sit on an internal backend network, unreachable from outside; only the API bridges frontend and backend.
Override filescompose.override.yml is applied automatically for local dev (hot-reload, exposed ports, debug). Production uses only the base file or an explicit -f set.
Per-environment env files.env (local), injected variables (CI), platform secrets (prod) — same compose file, different configuration.
Profilesprofiles: enable optional services (e.g. a seed job, a mailhog) only when requested.
 
# Local dev (base + override applied automatically)
docker compose up -d

# Explicit production composition (no dev override)
docker compose -f docker-compose.yml -f compose.prod.yml up -d
NoteKeep dev and prod differences in override files, not in branches of a single file. The base file should be the production-truthful definition; overrides add local conveniences.

7Configuration & secrets

Configuration is supplied by the environment, never hardcoded. Document every variable in .env.example; keep the real .env out of version control.

ContextWhere config/secrets liveRule
Local development.env (gitignored), from .env.exampleFake/local values only.
CI pipelineGitHub Actions secrets (repo or org)Injected as ${{ secrets.NAME }}; masked in logs.
Deployment targetGitHub Environments secrets (per env) or a platform secrets managerScoped per environment with protection rules.
 
# Set repository/environment secrets from the CLI
gh secret set DATABASE_URL --body "postgresql://..."
gh secret set REGISTRY_TOKEN --env production

GitHub Environments

Define development, staging and production environments. Each holds its own secrets and can require reviewers, wait timers and branch restrictions before a job targeting it runs — the mechanism for deployment approvals and environment segregation in CI/CD.

CautionNever commit secrets. Add .env to .gitignore before the first commit. Prefer short-lived credentials: for cloud deploys use OIDC federation (permissions: id-token: write) to mint temporary credentials instead of storing long-lived cloud keys as secrets. See the companion Secret-Scanning and OAuth/OIDC/JWT references.

8CI/CD with GitHub Actions

A workflow is a YAML file in .github/workflows/. It runs on events (triggers), executes jobs (on runners) made of steps (shell commands or reusable actions).

# .github/workflows/ci.yml — runs on every PR and push to main
name: ci
on:
  pull_request:
  push: { branches: [ main ] }

permissions: { contents: read }      # least privilege by default

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # retrieve the source
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: "pip" }   # dependency cache retrieval
      - run: pip install -r requirements.txt
      - run: pytest -q                     # fail the job (and the PR) on test failure
Workflow anatomy
ElementRole
on (triggers)Events that start the workflow: pull_request, push, schedule, workflow_dispatch, release.
jobsUnits of work; run in parallel by default; sequence with needs.
stepsOrdered commands/actions within a job.
uses / runInvoke a reusable action / run a shell command.
permissionsScope the job's GITHUB_TOKEN to least privilege.
matrixRun a job across multiple versions/OSes in parallel.
cachePersist and retrieve dependencies between runs for speed.

Applying CI/CD correctly

  • CI on every PR — build, test, lint; make these required status checks for merging to main.
  • Fail fast and loudly — a failing test or lint must fail the job; do not continue-on-error on gates.
  • Least privilege — set permissions explicitly; grant packages: write/id-token: write only where needed.
  • Pin actions — reference actions by major tag, and by commit SHA for anything security-sensitive.
  • Separate CI from CD — CI validates; a separate release workflow publishes and deploys, often on a tag or on merge to main.
  • Cache dependencies — retrieve from cache to keep runs fast; keep the cache key tied to the lockfile.

9Build, publish & retrieve

The release pipeline builds the image, publishes it to a registry, and the deployment step retrieves (pulls) it. GitHub Container Registry (GHCR) integrates with the built-in GITHUB_TOKEN.

# .github/workflows/release.yml — build & publish an image to GHCR
name: release
on:
  push: { branches: [ main ] }
  release: { types: [ published ] }

permissions:
  contents: read
  packages: write                        # required to push to GHCR

jobs:
  build-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }},ghcr.io/${{ github.repository }}:latest

Artifacts vs. images

MechanismUsePublish / retrieve
Workflow artifactPass build output between jobs; retain test reports/SBOMs after a run.actions/upload-artifact / download-artifact
Container imageThe deployable unit.Push to GHCR; docker pull on deploy.
Dependency cacheSpeed up repeated builds.actions/cache (keyed on the lockfile)

Deployment: retrieving the image

# On the deployment target (or a deploy job), pull the published image and run it
echo ${{ secrets.GHCR_TOKEN }} | docker login ghcr.io -u <user> --password-stdin
docker pull ghcr.io/<user>/my-app:<sha>
docker compose -f docker-compose.yml -f compose.prod.yml up -d

Target a GitHub Environment (environment: production) on the deploy job to enforce approvals and inject production-scoped secrets. Deploy immutable, SHA-tagged images rather than latest so a deployment is exactly reproducible and reversible.

10Makefile conventions

A Makefile gives the project one command vocabulary that is identical locally and in CI, hiding longer underlying commands. Keep targets short, declared .PHONY, and self-documenting.

# Makefile — '>' recipe prefix is robust to editors that strip tabs
.RECIPEPREFIX = >
.PHONY: help up down build test lint scan deploy clean

help:                 ## list targets
> @grep -E '^[a-z-]+:.*##' $(MAKEFILE_LIST) | sed 's/:.*##/ —/'

up:                   ## start the stack locally
> docker compose up -d --build

down:                 ## stop the stack
> docker compose down

test:                 ## run tests
> docker compose run --rm api pytest -q

lint:                 ## run linters/formatters
> ruff check . && ruff format --check .

clean:                ## remove containers and volumes
> docker compose down -v
PracticeReason
Declare .PHONY targetsPrevent conflicts with files of the same name.
A help target as defaultDiscoverability; one place lists what the project can do.
Thin wrappers over real toolsThe Makefile orchestrates; it does not reimplement logic.
Same targets used by CILocal and pipeline run identical commands (make test, make lint).
Variables for versions/pathsSingle point of change; no duplication.

11End-to-end walkthrough

From empty directory to a running, continuously delivered application:

  1. Initialize — git init; add .gitignore, README.md, LICENSE, .env.example; first commit.
  2. Create the remote — gh repo create; push main; enable branch protection.
  3. Write the application — minimal runnable service with a /health endpoint.
  4. Containerize — add Dockerfile and .dockerignore; build locally.
  5. Compose — add docker-compose.yml (app + db + cache, segregated networks); make up runs the stack.
  6. Configuration — move all config to environment variables; document in .env.example.
  7. CI — add ci.yml (checkout, cache, install, test, lint); make it a required check.
  8. Secrets & environments — set repository/environment secrets; define production with required reviewers.
  9. CD — add release.yml (build, push image to GHCR, SBOM, deploy pulling the SHA-tagged image).
  10. Iterate via PRs — feature branch → PR → CI green → review → merge → release → deploy.
# The everyday loop, identical on any machine
git switch -c feat/x
# ... change code ...
make test && make lint         # validate locally
git commit -am "feat: x" && git push -u origin feat/x
gh pr create --fill            # CI runs; merge when green and reviewed

12Best-practice checklist

Repository

  • Protected main; PRs + required checks + review.
  • Short-lived feature branches; small, focused PRs.
  • Conventional, descriptive commit messages.
  • .gitignore, .dockerignore, LICENSE, current README.
  • Dependabot/Renovate enabled for updates.

Containers

  • Pinned base images; multi-stage; non-root; healthcheck.
  • No secrets in images; inject at runtime.
  • Segregated Compose networks; dev/prod via overrides.

CI/CD

  • CI on every PR; fail fast; required status checks.
  • Least-privilege permissions; pinned actions.
  • Dependency caching; separate CI and CD workflows.
  • Immutable, SHA-tagged images; deploy by digest/SHA.
  • Environments with secrets + approvals; OIDC over stored cloud keys.

Operability

  • One command to run (make up) and to test (make test).
  • Config via environment; documented in .env.example.
  • SBOM and image scan in the release pipeline.
