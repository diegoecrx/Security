Software Composition Analysis

Identification and risk assessment of the open-source and third-party components an application depends on — including transitive dependencies — covering known vulnerabilities, prioritization, supply-chain threats, SBOM, licence compliance, integration and tooling.

1Definition & scope

SCA inventories the third-party and open-source components an application incorporates — both direct dependencies (declared) and transitive dependencies (pulled in by other dependencies) — and assesses them for known vulnerabilities, licence obligations, and integrity/provenance risk. Open-source code constitutes the majority of a typical codebase, and most vulnerable components are transitive, so the dependency graph cannot be assessed manually at scale.

SCA targets reused code; SAST and DAST target first-party code. All three are required for coverage of a complete application.

2Analysis mechanism

  1. Inventory — parse dependency manifests and lockfiles (package-lock.json, pom.xml, requirements.txt, go.sum, …); optionally fingerprint files or scan container image layers.
  2. Dependency resolution — build the full dependency graph, resolving transitive dependencies and exact versions.
  3. Vulnerability matching — match component + version against advisory databases: NVD (CVE/CVSS), OSV, GitHub Advisory Database (GHSA), and vendor research.
  4. Reachability analysis — determine whether application code invokes the vulnerable function/path, distinguishing exploitable from merely present.
  5. Licence analysis — identify each component's licence and classify obligations/risk.
  6. SBOM generation — emit a machine-readable inventory (SPDX or CycloneDX).

3Vulnerability prioritization

Matching every component against every CVE produces more findings than can be actioned. Prioritization combines three independent signals:

SignalQuestionSource
CVSSHow severe is the flaw?Base/temporal/environmental score, 0–10
EPSSHow likely is exploitation in the wild?Exploit Prediction Scoring System (probability)
ReachabilityCan this application reach the vulnerable code?Static call-path analysis
KEVIs it already being exploited?CISA Known Exploited Vulnerabilities catalogue

Reachable + high-EPSS or KEV-listed findings are remediated first; unreachable or low-likelihood findings are batched into routine upgrades. This is the primary lever for reducing SCA noise.

4Supply-chain threats

Beyond vulnerable components (unintentional flaws), SCA increasingly addresses malicious components (deliberate compromise):

ThreatDescription
Malicious packageA package published to execute attacker code (data theft, backdoor) on install or use.
Dependency confusionA public package with the same name as an internal one is resolved in preference, substituting attacker code.
TyposquattingA malicious package named a keystroke away from a popular one (e.g. colour vs color).
Integrity compromiseA legitimate package or its distribution is tampered with; mitigated by hash/signature verification and pinned versions.

5Worked example — transitive vulnerability (Log4Shell, CVE-2021-44228)

A single declared dependency resolves a vulnerable component several levels deep. The vulnerable library was never added directly:

your-app
└─ spring-boot-starter-web
   └─ spring-boot-starter-logging
      └─ log4j-to-slf4j
         └─ log4j-core : 2.14.1   # CVE-2021-44228, CVSS 10.0 (transitive, depth 4)
VulnerabilityCVE-2021-44228 Critical · CVSS 10.0
Componentlog4j-core : 2.14.1 (transitive)
ReachableYes — logging path exercised by request handling
RemediationUpgrade to log4j-core 2.17.1+ (override the managed version)

Only tooling or an SBOM surfaces a transitive component at this depth; it is not visible in the application's declared manifest.

6SBOM

A Software Bill of Materials is a machine-readable inventory of every component in a build. Standard formats are SPDX and CycloneDX. SCA both generates SBOMs (for your software) and consumes them (ingesting suppliers' SBOMs to assess inherited risk). A current SBOM reduces incident response to a query: on disclosure of a new component vulnerability, affected software is identified directly rather than through manual investigation. SBOM production is increasingly a regulatory and contractual requirement (US EO 14028, EU Cyber Resilience Act).

7Licence compliance

Each component carries a licence with obligations. SCA identifies licences and classifies risk — permissive (MIT, Apache-2.0, BSD), weak copyleft (LGPL, MPL), and strong copyleft (GPL, AGPL). A strong-copyleft component linked into proprietary software can create distribution obligations and legal exposure; SCA flags these before release. Licence analysis is often the feature that engages Legal and Procurement stakeholders.

8CI/CD integration & limitations

Integration pointFunction
IDE / pre-commitWarn on a vulnerable or badly-licensed dependency before it is added.
Pull requestScan changed dependencies; open automated upgrade PRs (Dependabot/Renovate pattern).
CI buildFull scan; gate on critical/reachable findings; emit SBOM.
Registry / proxyPolicy firewall blocking known-bad packages from being resolved.
Continuous monitoringRe-alert when a new CVE is published against an already-shipped component.

Limitations: detects only known (published) vulnerabilities — no coverage of undisclosed flaws or first-party code; version-level matching can flag issues that are not reachable in context (managed via reachability analysis); quality depends on advisory-database coverage; upgrades can introduce breaking changes, requiring a reliable test suite. Document and time-box vulnerability exceptions (risk acceptance) with owner, rationale and expiry.

10Operational best practices

  • Prioritize by reachability + EPSS/KEV + severity; do not pursue a zero-CVE backlog.
  • Automate upgrades with fix PRs and a strong test suite.
  • Generate and retain an SBOM per release; consume suppliers' SBOMs.
  • Scan application manifests and container/OS packages.
  • Enforce registry-level policy to block known-bad and unvetted packages.
  • Record vulnerability exceptions with owner, justification and expiry.
  • Monitor continuously — new advisories affect already-shipped versions with no code change.

12Terminology & references

Terminology

  • Direct / transitive dependency — declared / pulled in indirectly.
  • CVE / CVSS — vulnerability identifier / severity score.
  • EPSS — exploitation-probability score.
  • KEV — CISA Known Exploited Vulnerabilities.
  • Reachability — whether code can reach the vulnerable path.
  • SBOM — Software Bill of Materials (SPDX/CycloneDX).
  • Dependency confusion / typosquatting — name-based substitution attacks.
