Project Operations on Windows 11 with PowerShell

Install, configure, run, sync, deploy and continuously manage a GitHub-hosted project — locally and remotely — using PowerShell on Windows 11. Covers the toolchain (winget), Git/GitHub configuration, running the container stack, secrets, multi-machine synchronization, remote repository and pipeline control via the GitHub CLI, deployment, and scheduled continuous management.

1Scope & operating model

This runbook operates the SecureBank project (or any equivalent GitHub repository) entirely from PowerShell on Windows 11. The lifecycle is: install the toolchain → configure Git/GitHub → clone → run locally → manage secrets → synchronize between machines → control the remote repo and pipelines → deploy → continuously manage.

ElementChoice
ShellPowerShell 7 (pwsh). Windows PowerShell 5.1 works for most commands; v7 is recommended for consistency with cross-platform scripting.
Package managerwinget (App Installer, built into Windows 11).
Source controlGit + GitHub; remote origin is the single source of truth across machines.
Remote controlGitHub CLI (gh) for repos, PRs, secrets, workflows, releases.
RuntimeA container engine for local runs; optional if images are built only in CI.
WSL-freeThis runbook does not use WSL. Container engines on Windows normally require WSL2 or Hyper-V; see Section 2 for WSL-free engine options (Hyper-V backend, Podman, or CI-only builds). All Git/GitHub operations are native PowerShell and require no container engine at all.

2Toolchain installation (winget)

Run in an elevated PowerShell for machine-wide installs (Start → "PowerShell" → Run as administrator), or omit elevation for user-scope packages.

# Core toolchain
winget install --id Microsoft.PowerShell -e          # PowerShell 7 (pwsh)
winget install --id Git.Git -e
winget install --id GitHub.cli -e                      # gh
winget install --id Microsoft.VisualStudioCode -e

# 'make' is optional on Windows (PowerShell scripts in Section 11 replace it)
winget install --id ezwinports.make -e

# Verify
pwsh -v; git --version; gh --version

Container engine (choose one; WSL-free options first)

OptionInstall / note
Docker Desktop (Hyper-V backend)winget install --id Docker.DockerDesktop -e, then in Settings disable the WSL2 engine and enable the Hyper-V backend (requires Hyper-V/Windows Pro).
Podmanwinget install --id RedHat.Podman -e; podman machine init --provider hyperv to avoid WSL. Docker-compatible CLI.
No local engine (CI-only)Skip a local engine entirely; build and run images in GitHub Actions. Develop the app natively (Python/Node installed via winget) and use the pipeline for containers.
NoteAfter installing, close and reopen PowerShell so PATH updates. Check what is available with winget list. Update everything later with winget upgrade --all (Section 10).

3One-time configuration

PowerShell execution policy

# Allow local scripts (signed remote) for the current user
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Git identity and cross-platform line endings

git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf input    # don't rewrite LF to CRLF on commit
git config --global pull.rebase true      # linear history on pull

Commit a .gitattributes with * text=auto eol=lf so line endings are consistent across your two machines regardless of local settings.

GitHub authentication

# Interactive: choose HTTPS or SSH; gh stores the credential securely
gh auth login
gh auth status

SSH alternative (built-in OpenSSH on Windows 11):

ssh-keygen -t ed25519 -C "you@example.com"
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add $env:USERPROFILE\.ssh\id_ed25519
gh ssh-key add $env:USERPROFILE\.ssh\id_ed25519.pub -t "win11-main"
NotePerform Section 3 once per machine. Everything else (clone, run, sync) is repeatable and identical on both your machines.

4Acquire the project (clone)

# Pick a consistent location on each machine
$root = "$env:USERPROFILE\source\securebank"
New-Item -ItemType Directory -Force (Split-Path $root) | Out-Null

# Clone with the GitHub CLI (or: git clone git@github.com:USER/securebank.git $root)
gh repo clone USER/securebank $root
Set-Location $root

# Create the local .env from the template (never commit the real .env)
Copy-Item .env.example .env
notepad .env                      # fill in local/fake values

5Run locally

# Start the stack (Docker or Podman; 'docker compose' works with both CLIs)
docker compose up -d --build

# Check health
Invoke-RestMethod http://localhost:8000/health

# Follow logs / stop
docker compose logs -f
docker compose down

Environment variables in PowerShell

# Session-only
$env:APP_MODE = "vulnerable"

# Persist for the user (survives new sessions)
[Environment]::SetEnvironmentVariable("APP_MODE", "vulnerable", "User")

# Load a .env file into the current session (simple parser)
Get-Content .env | Where-Object { $_ -match '^\s*[^#].*=' } | ForEach-Object {
  $k,$v = $_.Split('=', 2); $env:$($k.Trim()) = $v.Trim()
}

If make is installed, the project's targets work in PowerShell too: make up, make test. Otherwise use the .ps1 wrappers in Section 11.

ScopeMechanism (PowerShell)Rule
Local app config.env file (gitignored)Fake/local values only; never commit.

# Optional encrypted local vault for developer secrets
Install-Module Microsoft.PowerShell.SecretManagement, Microsoft.PowerShell.SecretStore -Scope CurrentUser
Register-SecretVault -Name LocalStore -ModuleName Microsoft.PowerShell.SecretStore -DefaultVault
Set-Secret -Name GHCR_TOKEN -Secret "ghp_xxx"
$token = Get-Secret GHCR_TOKEN -AsPlainText

# Push a secret to GitHub for the pipeline
gh secret set DATABASE_URL --body "postgresql://..."
CautionNever place real secrets in .env, scripts, or command history you commit. Keep .env gitignored; store real credentials in the SecretStore vault or in GitHub secrets. Prefer OIDC for cloud deploys over long-lived stored tokens (see OAuth-OIDC-JWT.html, Secret-Scanning.html).

7Synchronize across machines

The remote is authoritative. Each machine pulls before work and pushes after. The flow below keeps a main machine and a personal machine in step.

# Start of a session: get the latest
git fetch origin
git status
git pull --rebase

# ... make changes ...
git add -A
git commit -m "describe the change"
git push

# On the other machine: replicate
git pull --rebase
SituationPowerShell / git handling
Uncommitted local work when pullinggit stash → git pull --rebase → git stash pop
Both machines changed maingit pull --rebase replays local commits on top; resolve any conflict, then git rebase --continue
Check divergencegit log --oneline --graph origin/main..HEAD
Discard local and match remote (destructive)git reset --hard origin/main — use deliberately
NoteUse feature branches and PRs rather than committing directly to main; this isolates in-progress work per machine and exercises the CI gates. The sync.ps1 helper (Section 11) wraps the safe fetch/stash/pull sequence.

8Remote repo & pipeline control

The GitHub CLI manages the remote entirely from PowerShell — no browser needed.

# Branches & pull requests
git switch -c feat/x; git push -u origin feat/x
gh pr create --fill
gh pr status
gh pr merge --squash --delete-branch

# Pipelines: list, watch, inspect, re-run
gh run list
gh run watch                         # live status of the latest run
gh run view --log                     # retrieve logs
gh run view --log-failed
gh run rerun <run-id>
gh workflow run release.yml          # trigger a workflow_dispatch

# Repository administration
gh repo view --web
gh secret list
gh release create v1.0.0 --generate-notes
TaskCommand
Open a PR for the current branchgh pr create --fill
Watch the current pipelinegh run watch
Retrieve failed-step logsgh run view --log-failed
Trigger a deploy workflowgh workflow run release.yml -f environment=production
Download a build artifact/SBOMgh run download <run-id> -n sbom

9Deploy

Pipeline-driven (recommended)

# Trigger the release workflow; it builds, pushes to GHCR, and deploys
gh workflow run release.yml -f environment=production
gh run watch

Deployment to a protected GitHub Environment pauses for approval; approve from gh or the web UI. The pipeline deploys an immutable, SHA-tagged image.

Manual image build and publish from PowerShell

$img = "ghcr.io/USER/securebank:$(git rev-parse --short HEAD)"
docker build -t $img .\application\backend
$env:CR_PAT = Get-Secret GHCR_TOKEN -AsPlainText
$env:CR_PAT | docker login ghcr.io -u USER --password-stdin
docker push $img

Deploy to a remote host over PowerShell Remoting (WinRM/SSH)

# Run deployment commands on a remote Windows host
$s = New-PSSession -HostName deploy-host -UserName deployer   # SSH transport
Invoke-Command -Session $s -ScriptBlock {
  Set-Location C:\apps\securebank
  git pull --rebase
  docker pull $using:img
  docker compose -f docker-compose.yml -f compose.prod.yml up -d
}
Remove-PSSession $s

10Continuous management

Keep both machines current, the stack healthy, and dependencies patched — scheduled with Windows Task Scheduler driven by PowerShell.

Scheduled auto-sync (pull latest on a schedule)

$action  = New-ScheduledTaskAction -Execute "pwsh" `
  -Argument '-NoProfile -File C:\Users\You\source\securebank\scripts\sync.ps1'
$trigger = New-ScheduledTaskTrigger -Daily -At 8am
Register-ScheduledTask -TaskName "securebank-sync" `
  -Action $action -Trigger $trigger -Description "Pull latest from origin"

Health monitor (restart if unhealthy)

try {
  $r = Invoke-RestMethod http://localhost:8000/health -TimeoutSec 5
  if ($r.status -ne "ok") { throw "unhealthy" }
} catch {
  docker compose restart api
  Write-Output "$(Get-Date -Format o) restarted api" | Add-Content .\logs\health.log
}

11Helper scripts

Keep operational scripts in scripts\ in the repo so both machines share them. They give a consistent vocabulary (the PowerShell equivalent of the Makefile).

ScriptPurpose
setup.ps1Install toolchain (winget), configure git/gh, create .env.
sync.ps1Safe fetch → stash → pull --rebase → stash pop.
up.ps1 / down.ps1Start / stop the compose stack.
deploy.ps1Build, tag by SHA, push to GHCR, trigger/await the release.
scan.ps1Run local scanners into reports\.
 
# scripts\sync.ps1 — safe synchronization
$ErrorActionPreference = "Stop"
Set-Location $PSScriptRoot\..
$dirty = (git status --porcelain)
if ($dirty) { git stash push -u -m "sync-autostash" }
git fetch origin
git pull --rebase origin (git rev-parse --abbrev-ref HEAD)
if ($dirty) { git stash pop }
Write-Output "Synced $(git rev-parse --short HEAD)"
NoteRun scripts with pwsh -NoProfile -File .\scripts\sync.ps1. Keep them idempotent and safe to re-run; have them exit 1 on failure so Task Scheduler and CI detect errors.

12Troubleshooting

SymptomCause / resolution
running scripts is disabledExecution policy. Set-ExecutionPolicy -Scope CurrentUser RemoteSigned.
Git shows all files modifiedLine endings. Set core.autocrlf input and add .gitattributes (* text=auto eol=lf).
docker: error during connectEngine not running. Start Docker Desktop / podman machine start.
Port 8000 already in useGet-NetTCPConnection -LocalPort 8000 → stop the owning process, or change the mapped port.
gh: not authenticatedgh auth login / gh auth status.
Long-path errors on checkoutgit config --global core.longpaths true.
Rebase conflict during pullResolve files, git add, git rebase --continue; or git rebase --abort.
Scheduled task did not runUse absolute paths and -NoProfile; run pwsh not powershell if v7 required; check Task Scheduler history.
