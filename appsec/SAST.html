1Definition & scope

SAST analyzes an application's source code, bytecode or compiled binary statically — the artifact is inspected, not run. Because the analyzer has full visibility into internal structure (all functions, branches and paths), it is a white-box technique. It identifies security-relevant defects in first-party code: injection, unsafe data handling, weak cryptography, hardcoded secrets, unsafe memory operations and similar classes, located at a specific file and line.

SAST operates at the Code and Build stages of the SDLC and can run before the application is executable. It is a core control in secure-development frameworks (OWASP ASVS verification requirements, OWASP SAMM, NIST SSDF practice PW.8). It is complementary to, not a substitute for, DAST (runtime testing), SCA (third-party components) and secret scanning.

2Analysis mechanism

A SAST engine constructs a structural model of the program, then reasons over it. The typical pipeline:

  1. Lexing & parsing — tokenize the source and build an Abstract Syntax Tree (AST) representing syntactic structure.
  2. Semantic model — resolve symbols, types and scopes; build a control-flow graph (CFG) per function and a call graph across functions.
  3. Data-flow analysis — track how values propagate through assignments, calls and returns, intra- and inter-procedurally.
  4. Taint analysis — the core security analysis: determine whether untrusted input reaches a sensitive operation without adequate neutralization.
  5. Rule evaluation & reporting — match findings against a rule set; emit location, CWE, severity and the data-flow trace.

Taint analysis: sources, sinks, sanitizers

TermDefinitionExamples
SourcePoint where untrusted/attacker-controllable data enters the program. Data from a source is tainted.HTTP parameters, request bodies, headers, file contents, message queues
SinkSensitive operation that must not receive tainted data unmodified.SQL query execution, OS command, HTML output, file path, deserializer
SanitizerOperation that neutralizes taint, making data safe for a given sink.Parameterized queries, context-aware output encoding, input validation, allow-listing

A finding is raised when a feasible path exists from a source to a sink with no applicable sanitizer on the path. Analysis quality depends on interprocedural precision (following taint across function and file boundaries), path/field sensitivity, and the completeness of the source/sink/sanitizer models for the target language and frameworks.

Code-quality findings (maintainability, style) are distinct from security findings and should be tracked separately; conflating them dilutes the security signal.

4Vulnerability coverage

SAST classifies findings against the CWE (Common Weakness Enumeration) taxonomy and maps to the OWASP Top 10. Coverage is strong for defects expressed in code structure and data flow, weaker for defects requiring runtime or environmental context.

5Rules & tuning

Detection accuracy is governed by the rule set. Rules exist in layers:

  • Built-in rules — vendor/community base coverage for common weaknesses.
  • Language-specific rules — tuned to a language's idioms and dangerous APIs.
  • Framework-specific rules — model the sources, sinks and sanitizers of a framework (e.g. Spring, Django, Express, React) so taint tracking is accurate.
  • Custom rules — organization-defined patterns: banned functions, internal sanitizer recognition, mandatory API usage, proprietary sink definitions.

False-positive and exception management

SAST false-positive rates are non-trivial and must be managed operationally, or developers disengage. Mechanisms:

  • Triage — confirm exploitability/validity before assigning remediation.
  • Suppression / exception management — durably record a reviewed false positive or an accepted risk (with owner, rationale, and expiry) so it does not re-alert on every scan.
  • Baselining — separate pre-existing findings from newly introduced ones so a legacy backlog does not block new work.

6Worked example — SQL injection (CWE-89)

Vulnerable handler (Python). User input reaches a query sink via string concatenation, with no sanitizer on the path:

def get_user(request):
    name = request.args.get("username")        # source: HTTP parameter (tainted)
    query = "SELECT * FROM users WHERE name = '" + name + "'"  # taint propagated
    return db.execute(query)                     # sink: SQL execution

Taint path: request.args.get("username") → name → query → db.execute(), with no parameterization or encoding.

WeaknessCWE-89 — SQL Injection Critical
Locationhandler, concatenation site and sink line
ConditionTainted input reaches a SQL sink with no parameterization/encoding
RemediationUse a parameterized query (prepared statement); data and command sent separately

Remediated — the parameterized API is a recognized sanitizer for the SQL sink, so no path from source to sink remains unneutralized and the finding clears:

def get_user(request):
    name = request.args.get("username")
    query = "SELECT * FROM users WHERE name = %s"   # placeholder, not concatenation
    return db.execute(query, [name])         # parameter bound separately

8Limitations

  • False negatives — defects outside the rule set, or reached via models the engine does not resolve (reflection, dynamic dispatch, metaprogramming), are missed.
  • No runtime or environmental context — configuration, deployment, TLS, and server misconfiguration are out of scope (DAST territory).
  • Business-logic and authorization correctness — "a user can act on another user's object" is valid code; SAST cannot judge intent.
  • False positives — require triage and suppression workflow; unmanaged, they erode adoption.
  • Performance — deep interprocedural analysis is resource-intensive on large codebases; mitigated by incremental scanning.
  • Language/framework support — precision varies by engine and target stack.

10Operational best practices

  • Run incrementally on PRs; run full/deep scans on main and on a schedule.
  • Baseline existing findings; gate on newly introduced defects to avoid blocking on legacy debt.
  • Gate on high-severity, high-confidence findings; expand coverage as false positives are tuned out.
  • Author custom rules for internal sanitizers, banned APIs and proprietary sinks to cut false positives and catch organization-specific risk.
  • Maintain a suppression/exception process with owner, justification and expiry; review periodically.
  • Assign severity-based remediation SLAs; report trend (mean time to remediate, open criticals) rather than raw counts.
  • Deliver findings in the IDE and PR, not a separate portal, to preserve developer workflow.
  • Correlate with DAST and SCA; a SAST finding confirmed exploitable by DAST is a priority.

12Terminology & references

Terminology

  • AST — abstract syntax tree; parsed structural model of code.
  • CFG / call graph — control-flow within a function / call relationships across functions.
  • Taint analysis — tracking untrusted data from source to sink.
  • Source / sink / sanitizer — input point / sensitive operation / neutralizing operation.
  • Interprocedural — analysis that crosses function boundaries.
  • CWE — Common Weakness Enumeration.
  • White-box — testing with full internal visibility.
  • Baseline — recorded set of pre-existing findings.
